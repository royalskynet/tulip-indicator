# 改善計畫：比特幣底部信心指數

## 這個專案在做什麼（白話）

這是一支觀察比特幣市場狀態的小工具，不是自動交易機器人。
它向公開資料來源讀取七種市場與鏈上訊號。
再把訊號換算成同一個分數，方便每天追蹤。
分數較高，表示目前條件較接近它定義的「底部」。
這不代表一定會上漲，也不是獲利保證。

平常可以看完整表格，或產生適合貼到聊天視窗的摘要。
每天的結果會留在自己電腦的歷史資料庫。
資料不齊時，會顯示資料涵蓋率。
可用訊號不到三個時，就拒絕評分，避免讓缺資料看起來像行情判斷。
這次保留原本的計分方式與這個保護措施。

## 可以運用的現成輪子

「輪子」就是別人已經維護好的工具，能用就不用自己重寫。
本專案以 Python 內建工具優先，不增加執行時套件。

| 現在自己寫的部分 | 建議的成熟工具 | 裁決 | 理由 |
|---|---|---|---|
| 自行拆解命令列文字 | argparse（Python 內建） | 採用 | 自動提供說明與錯誤提示，不必安裝套件。 |
| 自己管理資料庫何時關閉 | contextlib.closing（內建） | 採用 | 結束或發生錯誤都會關閉連線，寫入仍保留交易提交。 |
| 只有程式裡的自我檢查 | unittest、unittest.mock（內建） | 採用 | 可用假資料驗證斷線與缺資料，不耗 API 額度。 |
| 手動確認每次修改沒壞 | GitHub Actions | 採用 | 推送後自動跑離線測試，不需要市場金鑰。 |
| 自己寫重試迴圈 | Tenacity | 借鏡 | 重試分類與隨機等待值得參考；直接使用會新增套件，本次不裝。 |
| 自己發送網路請求 | urllib.request（內建） | 採用 | 延用現有做法與逾時，不為這次小改導入 HTTPX。 |
| 自己寫資料庫操作 | sqlite3（內建） | 採用 | 資料量小，沒有必要導入 SQLAlchemy。 |

選擇依據是：維護成本低、離線可測、日常使用不用多裝東西。
不因為工具有名就導入；先看現在的規模是否真的需要。

## 優化路線

### 本次 PR 已做

1. 改用內建的參數解析工具。
   不帶參數仍顯示完整表格。
   `--summary` 仍顯示摘要。
   `--selftest` 仍只做離線檢查。
   `--history N` 仍查最近 N 筆歷史，省略 N 時預設為 30。
   N 必須是正整數；打錯時會提供提示，不會直接印出程式錯誤堆疊。
2. 讓資料庫用完就關閉。
   寫入時仍會正式儲存，不是只有把連線關掉。
3. 網路重試耗盡後，保留最後一次失敗原因並顯示警告。
   缺少訊號時也會指出是哪個訊號。
   警告走錯誤輸出，不混入原本的表格或聊天摘要。
4. 加入不用連網的自動測試。
   涵蓋參數、部分資料重新配重、訊號太少拒絕評分。
   也檢查歷史寫入、讀回，以及資料庫連線有沒有關閉。
   測試資料庫放在暫存區，不碰日常歷史。
5. 加入 GitHub Actions，並補上 README 測試指令。

### 之後可做（依價值排序）

1. 把資料來源失敗分成限流、服務故障、格式改版。
   好處：知道是應該稍後重試，還是需要修改讀取方式。
   先借鏡 Tenacity 的重試分類，不急著加套件。
2. 為每種資料來源準備固定的範例回應。
   好處：網站改欄位時更容易定位，不必一直打公開 API。
3. 加入短時間快取與限流等待。
   好處：避免同一天重跑太多次，用掉免費額度。
   仍優先用內建時間與檔案工具，並清楚標示資料時間。
4. 讓資料庫寫入失敗有更白話的提示。
   好處：磁碟滿或目錄不能寫時，使用者知道怎麼處理。
5. 再評估是否需要抽出模組。
   目前單檔容易攜帶，不為了形式拆成大型架構。

## 怎麼確認這次沒有弄壞

執行 `python3 btc_bottom_score.py --selftest`。
再執行 `python3 -m unittest discover -s tests`。
兩個指令都不需要金鑰，也不連市場服務。
這些檢查驗證程式行為，不驗證投資策略能否獲利。
